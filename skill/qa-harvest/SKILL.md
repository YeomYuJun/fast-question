# qa-harvest

대상 폴더를 목록 → 주제 → 원문 읽기 → 초안 → 검사 → 적재 → 기록 순서로 처리해 Q&A 를 쌓는다.
사람은 등록분을 검토하지 않는다. 그래서 건수보다 정확성을 우선하고, 아래 규칙으로 품질을 지킨다.

## 원칙

- 등록 규칙의 원본은 `~/.claude/skills/qa/rules.md` 다. 시작할 때 읽고 모든 항목에 적용한다.
- 답은 원문을 읽고 쓴다. 파일 이름, 목록, 요약, 추측으로 답을 쓰지 않는다. 이 세션(서브에이전트 포함)에서 읽지 않은 파일은 근거로 달지 않는다.
- 이유를 원문(주석, 커밋 메시지, 문서)에서 확인하지 못했으면 "왜" 질문을 만들지 않는다. 확인한 동작만 "언제·어떻게" 질문으로 쓴다.
- 이번 회 상한을 넘기지 않는다(기본 60건). 한 파일에서 나온 항목은 5건까지다.
- 사용자에게 묻는 것은 0단계 범위뿐이다. 요청에 경로와 주제가 있으면 묻지 않는다.
- 외부 지식 그래프 도구에 의존하지 않는다. 탐색은 이 문서의 절차와 Claude 의 읽기·검색·서브에이전트로 한다.

## 0. 범위

- 대상 경로(여럿 가능), 대분류 이름(사업·프로젝트 이름), 이번 회 상한.
- `kb_categories` 에 같은 주제의 대분류가 있으면 그것을 쓴다(예: `사내 시스템 이관 사업`). 새로 만들지 않는다.
  새로 만들 때 대분류 이름은 대상 폴더 이름과 같게 짓고, `description` 에 이 분류에 넣는 것과 넣지 않는 것을 한 줄로 적는다. 그 분류에 이미 description 이 있으면 그 범위 밖의 질문은 만들지 않는다.
- 대상 경로마다 `kb_harvest` action=get 으로 지난 기록을 읽는다. 기록이 있으면 증분 모드다(2단계 끝 참고).

## 1. 목록 (결정적)

```
"{{FAST_QUESTION_ROOT}}/.venv/Scripts/python.exe" "~/.claude/skills/qa-harvest/inventory.py" "<경로1>" "<경로2>" --out "<스크래치>/inventory.json"
```

- 증분 모드면 지난 record 를 `<스크래치>/since.json` 으로 저장하고 `--since "<스크래치>/since.json"` 을 더한다.
- `~` 는 실제 홈 경로로 바꿔 쓴다. 경로에 공백이 있으므로 인자는 따옴표로 감싼다.
- 출력에서 볼 것
  - `repos[]`: `dirs`(모듈 분포), `hot_files`(자주 바뀐 파일), `fix_commits`(오류 수정 커밋과 바뀐 파일), `head`
  - `plain_dirs[]`: git 이 아닌 폴더(분석 자료, 설정, 정책 문서 묶음)
  - `documents[]`: 문서 파일(md, txt, xlsx, xls, csv, hwp, pdf, docx, pptx)

## 2. 주제 고르기

1. 대상 경로와 각 저장소의 README, CLAUDE.md, 설계·인수인계 문서를 먼저 읽어 시스템 이름과 용어를 익힌다.
2. 아래 순서로 주제를 고르고, 주제마다 읽을 파일과 예상 건수를 적은 표를 만든다. 상한 안에서 위쪽부터 채운다.
   1. 오류 수정 커밋 가운데 그 수정이 지금 코드에 남아 있는 것: 원인과 처리
   2. 설계·운영·이관 문서의 결정과 절차
   3. 자주 바뀐 핵심 클래스·설정의 이유와 동작 조건
   4. 설정 키(yml, properties)의 뜻과 기본값
   5. 빌드·배포·실행 절차와 이 PC 의 환경 정보
   6. 정책 문서(방화벽, 보안그룹, 망연계, 암호화 대상): 위치와 절차만
   7. 작업에 쓰인 기술의 일반 지식
3. 저장소가 크면(추적 파일 500개 이상) 모듈 단위로 서브에이전트(Explore 등 읽기 전용)에 맡긴다. 서브에이전트에게는 "이 모듈에서 rules.md 의 넣는 것에 해당하는 질문 후보와, 답을 확인한 file:line·인용"을 돌려 달라고 한다. 서브에이전트는 등록하지 않는다. 등록은 메인 세션 하나가 해서 중복 판정을 한 곳에서 한다.
4. 증분 모드: `since.changed` 와 `since.commits` 만 대상이다. 바뀐 파일마다 `kb_search` 로 `path:<파일 이름>` 을 찾아, 그 파일을 근거로 단 기존 항목은 qa Skill 조회 4번(근거를 다시 읽고 정리) 으로 처리한다.

## 3. 출처 유형별로 읽고 질문 만들기

| 출처 | 읽는 것 | 질문 형태 | 근거 |
|---|---|---|---|
| 소스 코드 | guard 절, 예외 처리, 재시도·타임아웃, 설정 기본값, 이유를 적은 주석 | `X 가 Y 하는 이유는?`, `X 가 실패하면?`, `X 는 언제 Y 하나?` | `auto` + 파일 + 심볼 anchor |
| git 이력 | `fix_commits` 의 제목, `git show --stat <sha>`, 바뀐 부분 | `X 가 Y 하던 문제의 원인은?` (지금 코드에 남은 것만) | 지금 파일 `auto`, 답변에 sha 앞 7자리 |
| md 문서 | 결정, 절차, 정책, 표 | `X 하려면?`, `X 를 Y 로 정한 이유는?` | `auto` + 파일 + 절 제목 anchor |
| xlsx·xls | 시트 이름, 머리행, 구분 열 | `X 목록은 어디에 있나?`, `X 신청 절차는?` | `auto` + 파일 + 시트 이름 anchor |
| pdf | Read 도구로 읽는다 | 문서와 같다 | `auto` + 파일 |
| 설정 파일 | 키와 값, 프로파일별 차이 | `<키> 의 뜻은?`, `<프로파일> 에서 X 가 다른 이유는?` | `auto` + 파일 + 키 anchor |
| 일반 지식 | 작업에 쓰인 개념만 | `X 와 Y 의 차이는?` | 없음 또는 공식 문서 `url`. 대분류 `일반 지식` |

- xlsx 는 시스템 Python(`python`, openpyxl 있음)으로 시트 이름과 처음 몇 행만 읽는다. 값을 옮겨 적지 않는다. hwp 처럼 읽을 수 없는 형식은 건너뛰고 보고에 적는다.
- 정책·보안 문서에서 IP, 포트 목록, 계정, 비밀번호 같은 값은 쓰지 않는다. 그 값이 어느 파일·시트에 있고 어떤 절차로 바꾸는지만 쓴다. `kb_add_many` 가 IP·비밀값·개인정보를 거부한다.
- 사람 정보(R&R 등)는 역할·팀 단위로 쓴다. 연락처는 쓰지 않는다.
- 로그·덤프 파일(`*.log`, `hs_err_*`)과 빌드 산출물(`*.class`, `*.jar`)은 읽지 않는다.

## 4. 초안

질문을 먼저 정하고 답은 나중에 쓴다. 답을 쓰다 보면 질문이 묻지 않은 내용이 끼어든다.

1. 질문 목록: 주제마다 질문만 먼저 적는다. 질문 하나에 사실 하나다. `kb_search` 의 `queries` 로 이미 있는 질문을 뺀다.
2. 답: 남은 질문마다 원문을 다시 열어 그 질문에만 답한다. 첫 줄이 질문에 바로 답하고, 덧붙일 사실은 `- ` 항목으로 나눈다(rules.md "답변" 표).

- 초안을 `<스크래치>/draft.json` 에 배열로 쓴다. 항목: `{"category", "question", "answer", "evidence", "quote", "ask_when"}`.
  - `quote`: 답의 근거가 된 원문을 그대로 옮긴 것(300자 이하). 근거가 있으면 필수다.
  - `ask_when`: 사용자가 이 질문을 다시 하게 되는 구체적인 상황 한 줄(예: `배포가 디스크 부족으로 실패했을 때`). 쓸 수 없으면 그 항목은 등록하지 않는다.
  - `quote`·`ask_when` 은 검사용이다. `kb_add_many` 는 이 칸을 저장하지 않는다.
- 분류: 대분류는 0단계 이름, 중분류는 대상(모듈, 시스템, 문서 묶음) 이름이다. 중분류는 한 회에 15개를 넘기지 않게 묶는다. 맞는 중분류가 없으면 `kb_add_category` 로 만든다.
- 형태소 분석이 잘못 자를 고유명사(시스템 이름, 사업 이름)는 적재 전에 `kb_dict` action=user_word_add 로 한 번에 넣는다. 사용자 단어를 바꾸면 색인을 다시 만든다. 원격 서버에 연결했으면 이 동작은 거부된다(서버 공용 사전이라 운영자가 넣는다). 넣지 말고 넘어간다.
- 같은 뜻의 다른 표기는 `kb_dict` action=synonym_add 로 묶는다.

## 5. 검사와 중복

1. 기계 검사. 문제가 0건이 될 때까지 고치고 다시 돌린다. 0건이 아니면 6단계로 가지 않는다.
   ```
   "{{FAST_QUESTION_ROOT}}/.venv/Scripts/python.exe" "{{FAST_QUESTION_ROOT}}/scripts/lint_draft.py" "<스크래치>/draft.json"
   ```
   등록 검사(길이, 답변 양식, 결정 경위·추정 표현, 민감 정보), `quote`·`ask_when` 유무, quote 의 식별자가 답에 있는지, 초안 안의 비슷한 질문, 파일당 5건을 본다.
2. 자기 검사. 항목마다 아래에 모두 "예" 여야 남긴다. 하나라도 "아니오" 면 고치거나 버린다.
   - 질문에 대상 이름이 있고, 대상이 둘 이상 묶여 있지 않다.
   - 답 첫 줄이 질문에 바로 답한다(질문 문형에 맞는 모양이다).
   - 답에 질문이 묻지 않은 대상(다른 서비스·모듈)이 없다.
   - 지금 동작만 쓰고, 날짜·결정 주체·"~로 바꿨다" 가 없다.
   - `ask_when` 이 구체적인 상황이다("궁금할 때" 는 불합격).
3. `kb_search` 의 `queries` 에 핵심어 2~3개를 넣어 같은 사실이 이미 있는지 본다. 있으면 그 항목을 `kb_update` 대상으로 옮긴다(답이 더 정확해질 때만).

## 6. 적재

- `kb_add_many` 의 `file` 에 초안 파일 절대경로를 주어 넣는다(파일 하나에 100건까지, 넘으면 파일을 나눈다). 항목을 도구 인자로 다시 옮겨 적지 않는다. 옮겨 적다 한글 한 글자가 다른 글자로 바뀐 채 등록된 사례가 있다.
- 적재 뒤 `kb_get` 이나 `kb_search` 로 읽은 질문·답변을 초안과 글자 단위로 대조하고, 다르면 `kb_update` 로 고친다.
- 결과를 항목별로 처리한다.
  - `error`: 메시지(형식 규칙, 분류 없음)대로 고쳐 다시 넣는다.
  - `similar_found`: 후보와 비교한다. 다른 사실이면 `force: true` 로 다시 넣고, 같은 사실이면 넣지 않는다.
- 같은 모듈에서 서로 이어지는 항목은 `kb_link` 로 잇는다.

## 7. 기록

- 대상 경로마다 `kb_harvest` action=set 으로 기록한다.
  `state` 예: `{"repos": {"<저장소 경로>": "<inventory 의 head>"}, "created": 12, "updated": 3, "skipped": {"이유 확인 불가": 4, "읽을 수 없는 형식": 2}, "note": "다음 회 후보: ..."}`
- 상한 때문에 다루지 못한 주제는 `note` 에 남겨 다음 회에 이어간다.

## 8. 보고

- 등록·수정 건수, 분류별 건수, 건너뛴 이유별 건수, 읽지 못한 파일 형식, 다음 회 후보를 적는다.
- 항목 목록은 대표 10건만 `등록: <질문> {{FAST_QUESTION_URL}}/#qa/<id>` 형식으로 적고 나머지는 화면 주소({{FAST_QUESTION_URL}}, 분류 패널)로 대신한다.
