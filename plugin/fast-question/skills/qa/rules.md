# Q&A 등록 규칙

이 파일이 fast-question 등록 규칙의 원본이다. qa Skill, qa-harvest Skill, MCP 서버 안내문은 이 파일을 따른다.
Claude 가 MCP 로 쓸 때 `kb_add`·`kb_add_many`·`kb_update`·`kb_evidence` 는 답변 양식, 금지 표현, 민감 정보를 검사해 위반이면 거부한다. 거부 메시지를 보고 고쳐서 다시 부른다.
민감 정보 거부 메시지는 걸린 위치(질문, 답변 몇째 줄, 근거)를 알려 준다. 값 자리에 `<pw>` 처럼 꺾쇠로 감싼 자리표시자만 쓰면 비밀값으로 보지 않는다.

이 DB 는 두 가지를 쌓는다. 사람이나 Claude 가 다음에 궁금해할 사실, 그리고 겪은 일의 기록(오류와 그 해결, 해 보고 안 된 방법, 쓰지 않기로 한 것)이다. 둘 다 확인한 사실만 담는다. 등록할지 망설여지면 등록하지 않는다. 사람은 등록분을 검토하지 않으므로 한 건이 틀리거나 쓸모없으면 그대로 남는다.

## 등록할 가치

양식에 맞는 사실이 모두 등록할 사실은 아니다. 한 건마다 "같은 프로젝트에서 다음에 일하는 사람이나 Claude 가 이 사실을 모르면 무엇을 다시 치르는가" 를 한 구절로 적어 본다. 적을 수 없거나 답이 "파일을 한 번 연다" 이면 등록하지 않는다.

이 DB 를 가장 자주 읽는 것은 다음 세션의 Claude 다. Claude 가 이미 아는 것(기술의 일반 지식)과 파일을 열면 그대로 보이는 것은 KB 에 없어도 잃지 않는다. KB 에 있어야 하는 것은 코드에 없는 사실(현장·환경, 사람에게 확인한 것, 쓰지 않기로 한 것)과 여러 곳을 이어 읽어야 나오는 사실이다.

등록은 그 사실이 다시 필요해진다는 예측이다. 무엇이 그런 사실인지는 이 물음으로 Claude 가 판단하고, 아래 목록은 예시다. 목록에 없어도 물음에 답이 있으면 등록한다.

후보는 방금 읽은 내용 전체가 아니라 조사한 경로에서 고른다. 읽기만 하면 다시 보이는 것은 적지 않아도 남아 있고, 조사해서 알아낸 것은 적지 않으면 사라진다.

- 읽기 전 예상과 달랐던 것. 이름이나 문서가 말하는 것과 실제 동작이 다르다
- 파일을 여러 개 이어 읽어야 알 수 있었던 것. 값이 한 곳에서 정해져 다른 곳을 거쳐 쓰인다
- 오류 문구·증상과 그 원인, 처리
- 하면 안 되는 것과 그 이유. 고치면 다른 것이 깨진다
- 쓰지 않기로 한 것, 없앤 것, 해 보고 안 된 방법과 그 이유. 코드에 남지 않아서 읽어서는 알 수 없고, 모르면 같은 것을 다시 제안하거나 다시 해 본다
- 사람에게 확인해서 알게 된 것. 코드와 문서에 없다
- `kb_search` 로 찾았는데 없어서 직접 알아낸 것. 필요했던 적이 이미 한 번 있다

같은 대상에서 골라도 가치가 갈린다.

| 등록한다 | 등록하지 않는다 |
|---|---|
| `관리자 API 가 새로고침마다 일부만 401 이 되는 원인은?` (모르면: 프록시 설정과 필터 코드를 다시 이어 읽는다) | `관리자 API 필터 클래스는 어느 패키지에 있나?` (이름으로 검색하면 나온다) |
| `health 가 503 이고 로그에 ErrCode=1111 이 나오면?` (모르면: 원인을 다시 추적한다) | `설치 절차 문서는 어디에 있나?` (폴더를 열면 보인다) |
| `decrypt 의 관용 동작을 고치면 안 되는 이유는?` (모르면: 결함으로 보고 고친다) | `현장 작업 문서 폴더에는 무엇이 들어 있나?` (목차다. 폴더가 바뀌면 틀린다) |
| `fast-question 에 등록분을 사람이 승인하는 화면이 없는 이유는?` (모르면: 그 화면을 다시 만들자고 제안한다) | `fast-question 의 검토 기능은 언제 없앴나?` (경위다. 지금 무엇을 할지 바꾸지 않는다) |

## 넣는 것

- 동작: 무엇이 언제 무엇을 하는지, 실패하면 어떻게 되는지
- 이유: 코드·설정이 지금 그렇게 되어 있는 이유(원문이나 사람에게 확인한 것만). 그 이유가 기대는 전제가 있으면 "재검토 조건" 대로 한 항목으로 쓴다
- 쓰지 않는 것과 그 이유: 검토했다가 쓰지 않기로 한 대안, 없앤 기능, 해 보고 안 된 방법. 지금도 유효한 제약으로 쓴다(`X 를 쓰지 않는 이유는?`). 해 보고 안 된 방법은 그때 본 오류 문구나 결과를 넣는다
- 절차: 무엇을 하려면 어떤 명령을 어떤 순서로 쓰는지. 문서에 그대로 적힌 절차는 옮기지 않고, 문서에 없는 단계와 순서를 어기면 생기는 일을 쓴다
- 위치: 이름으로 검색해서는 찾을 수 없는 값의 위치(어느 설정이 어느 파일의 어느 키에서 정해지는지)
- 오류의 원인과 처리
- 하면 안 되는 것과 그 이유
- 이름만으로는 알 수 없는 설정 키·값·코드의 뜻(그 값이 어느 코드에서 어떤 동작을 바꾸는지)
- 일반 지식은 사용자가 `/qa` 로 요청한 것만. 요청이 없으면 넣지 않는다

## 넣지 않는 것

- 결정 경위(누가 언제 무엇을 정했는지), 개발 이력, 바뀌기 전의 동작. 지금 동작과 그 이유만 쓴다. 쓰지 않기로 한 것과 그 이유는 경위가 아니라 지금 유효한 제약이므로 "넣는 것" 대로 넣되, 날짜와 정한 사람은 답에 쓰지 않고 근거(note)에 둔다
- 내부 구현 세부(테이블 열, 내부 함수 이름)로만 답이 되는, 사용자가 다시 물을 일이 없는 것
- 진행 상태, 할 일, 일정. 논의 중인 안과 결정 전인 것도 넣지 않는다
- 이름만 봐도 아는 것(예: `UserService 는 사용자 서비스인가`)
- 코드나 문서를 그대로 옮긴 것
- 문서·폴더가 어디에 있고 무엇이 들어 있는지(위치, 목차, 탭·시트 구성). 폴더를 열거나 이름으로 검색하면 나온다
- 이 세션에서 Claude 가 만들거나 고친 파일의 내용. 방금 쓴 것을 옮긴 것이고 사용자가 확정하기 전이라 바뀔 수 있다. 사용자가 `/qa` 로 요청할 때만 넣는다
- 확인하지 않은 추정. 확인하지 못했으면 등록하지 않는다
- 이 대화에만 해당하는 질문(예: `방금 그 명령은 왜 실패했나`)
- 지금 작업 중인 프로젝트와 무관한 평시 질문(언어 문법, 도구 사용법, 개념). 사용자가 `/qa` 로 요청할 때만 넣는다
- 비밀번호, 토큰, API 키, 개인 키
- 주민등록번호, 전화번호, 이메일 주소 같은 개인정보
- IP 주소 같은 내부 망 값. 값 대신 그 값이 적힌 위치(파일·시트)와 절차를 쓴다. 루프백(`127.0.0.1`)은 넣어도 된다

## 질문

질문 칸은 그 항목을 찾는 열쇠다. 검색은 대상 이름과 오류 문구가 질문·답변에 있는지를 보고 문장의 끝맺음은 보지 않는다. 그래서 끝맺음은 내용에 맞는 것을 고른다.

| 끝맺음 | 쓰는 때 | 예 |
|---|---|---|
| 묻는 문장 | 사실, 이유, 조건을 물을 때 | `인증 서버의 issuer 주소를 바꾸려면 무엇을 다시 만들어야 하나?` |
| 명사로 끝나는 구 | 절차, 방법, 목록 | `고친 Skill 원본을 설치본에 다시 반영하는 방법` |
| 증상·오류 문구 | 겪은 일의 기록 | `사내 Harbor 에서 crane pull 로 이미지를 받으면 실패함` |

- 한 줄, 가중 길이 300자 이하. 가중 길이는 공백을 포함해 한글·한자·전각 문자를 2자, 그 밖의 문자(영문·숫자·기호·공백)를 1자로 센다. 물음표는 붙여도 되고 붙이지 않아도 된다.
- 한 항목에 사실 하나, 기록이면 겪은 일 하나다. 대상이 `와·및·그리고·,` 로 둘 이상 묶이면 나눈다. 비교·차이를 묻는 질문(`A 와 B 의 차이는?`)은 한 사실이라 나누지 않는다.
- 주제 이름을 질문으로 쓰지 않는다. `배포 파이프라인 구축 이슈` 아래에 이슈 여러 건을 적으면 그 오류를 만났을 때 검색에 걸리지 않고, 한 건의 근거가 바뀌어도 항목 전체가 바뀐 것으로 판정된다. 이슈마다 항목을 따로 만들고 `kb_link` 로 잇는다.
- 질문만 읽어도 무엇에 대한 것인지 알 수 있게 쓴다. 대상 이름(파일, 클래스, 설정 키, 명령, 개념)을 넣는다.
  대상이 일반 명사(검색, 분류, 웹 서버, 저장소, 배포)면 시스템이나 프로젝트 이름을 붙인다.
  - 나쁨: `검색 문법은`
  - 좋음: `fast-question 검색창에서 쓸 수 있는 질의 문법은?`
- 답의 제목이 아니라 그 사실이 필요해지는 순간에 보이는 말로 쓴다. 그때 화면·로그에 보이는 오류 문구, 증상, 하려던 일을 그대로 넣는다. 검색은 대상 이름과 오류 문구로 들어온다.
  - 나쁨: `IpCheckFilter 의 X-Forwarded-For 처리 방식은?` (답을 아는 사람만 이 이름으로 찾는다)
  - 좋음: `관리자 API 가 새로고침마다 일부만 401 이 되는 원인은?`
  - 나쁨: `인증 중계 서버 설치 이슈` (주제 이름이다. 어떤 증상인지 없다)
  - 좋음: `인증 중계 서버 health 가 503 이고 로그에 ErrCode=1111 이 나옴`
- 한 번에 등록하는 질문이 `X 는?`, `X 의 뜻은?` 같은 한 가지 문형으로만 이어지면 파일을 위에서부터 옮기고 있는 것이다. "등록할 가치" 로 돌아가 조사 경로에서 다시 고른다.

## 답변

- 가중 길이 800자 이하, 6줄 이하. 가중 길이는 질문과 같은 방식으로 세고 공백과 줄바꿈을 1자씩 포함한다.
- 답에는 질문에 필요한 만큼 동작(무엇이 무엇을 해서), 결과(그래서 어떻게 되는지), 확인하거나 처리하는 법을 넣는다. `없다`, `코드 상수다` 처럼 다음에 무엇을 할지 알 수 없는 한 문장으로 끝내지 않는다.
- 첫 줄만으로 끝나는 짧은 사실은 같은 대상의 관련 사실과 묶어 한 항목으로 만든다. 질문의 대상은 하나로 두고, 둘째 줄부터 그 대상의 다른 측면(바꾸는 곳, 기본값, 예외)을 쓴다.
- 첫 줄은 질문에 바로 답한다. 1~2문장, 가중 길이 240자 이하. 질문이 묻지 않은 대상(다른 모듈·서비스)은 쓰지 않는다. 기록이면 첫 줄이 결론(원인, 또는 쓰지 않기로 한 이유)이다. 검색 결과에 여러 항목이 함께 나올 때 첫 줄만 보고 해당하는지 가린다.
- 둘째 줄부터는 필요할 때만 쓴다. `- ` 로 시작하고 한 줄에 한 사실을 개조체로 쓴다(마침표 없이, 가중 길이 240자 이하).
  한 줄에 사실을 쉼표로 이어 붙이지 않는다. 240자를 넘을 내용이면 항목으로 나눈다.
- 무엇이 무엇을 해서 어떻게 되는지 쓴다. 비유를 쓰지 않고 얼버무리지 않는다.
- 경로, 식별자, 명령은 원문 그대로 쓴다.
- 측정값, 버전에 따라 바뀌는 내용에는 기준을 붙인다(예: `2026-10-08 실측 2.5초`, `kiwipiepy 0.24.0 기준`).

### 기록

겪은 일(오류와 그 해결, 해 보고 안 된 방법, 쓰지 않기로 한 것)은 첫 줄에 결론을 쓰고, 둘째 줄부터 머리말을 붙인 항목으로 쓴다. 머리말은 아래 넷이고 해당하는 것만 쓴다.

- `- 상황: <무엇을 하다가 어떤 오류 문구·증상을 봤는지>`
- `- 원인: <첫 줄에 다 쓰지 못한 원인>`
- `- 해결: <한 것. 명령은 원문 그대로>` 해 보고 안 된 방법이면 `- 안 된 것: <한 것과 그 결과>` 를 함께 쓴다
- `- 전제: <이 해결이나 판단이 유효한 조건>` ("재검토 조건")

```
Q. 사내 Harbor 에서 crane pull 로 이미지를 받으면 실패함
A. <원인 한 문장>.
   - 상황: <받으려던 이미지와 그때 나온 오류 문구>
   - 안 된 것: <먼저 해 본 것과 그 결과>
   - 해결: <이미지를 받은 명령>
   - 전제: <이 방법이 통하는 조건>
```

- 날짜와 한 사람은 답에 쓰지 않고 근거(note)에 둔다. 답에는 지금도 참인 것만 남긴다.
- 해결 절차가 길어 6줄에 들어가지 않으면 절차를 `… 하는 방법` 항목으로 따로 만들고 `kb_link` 로 잇는다.
- 원인을 확인하지 못한 기록은 등록하지 않는다. 증상과 해결만 있고 원인을 모르면 다음에 같은 해결이 통하는지 판단할 수 없다.

### 재검토 조건

이유를 답하는 항목(`X 가 Y 하는 이유는?`, `X 를 쓰지 않는 이유는?`, `X 를 하면 안 되는 이유는?`)은 그 이유가 어떤 전제에 기대는지 확인했으면 마지막 항목에 `- 전제: <지금 참인 조건>. <그 조건이 어떻게 바뀌면 다시 판단하는지>` 로 쓴다.
읽는 쪽은 전제가 지금도 참이면 그 답을 따르고, 바뀌었으면 답을 근거로 삼지 않고 사용자에게 다시 판단할 때라고 알린다.
전제를 확인하지 못했으면 항목을 만들지 않는다. 추정한 전제는 쓰지 않는다. 머리말은 답의 언어를 따른다(영어 답이면 `- Premise:`).

질문 문형이 답 모양을 정한다.

| 질문 | 첫 줄 | 둘째 줄부터 |
|---|---|---|
| `X 하려면?`, `X 하는 방법` | 명령이나 첫 동작 | 이어지는 동작을 순서대로 |
| `<증상·오류 문구> 가 나옴`, `X 가 실패함` | 원인 | `- 상황:`, `- 안 된 것:`, `- 해결:`, `- 전제:` ("기록") |
| `X 의 뜻은?`, `X 는 무엇인가?` | `X 는 …다.` | 없음 |
| `X 가 Y 하는 이유는?` | `…때문이다.` | 그 결과(선택), `- 전제: …`(확인했으면) |
| `X 를 쓰지 않는 이유는?`, `X 가 없는 이유는?` | 쓰지 않는 이유 | 대신 쓰는 것, `- 전제: …`(확인했으면) |
| `X 를 Y 로 하면 <오류 문구·결과> 가 나온다` | 안 되는 원인 | 되는 방법 |
| `X 는 어디서 정해지나?` | 값이 정해지는 파일과 키 | 그 값이 거쳐 가는 곳(선택) |
| `X 가 실패하면?`, `X 는 언제 Y 하나?` | 조건과 결과 | 예외 조건(선택) |
| `<오류 문구·증상> 이 나오면?` | 원인 | 확인하는 법, 처리 |
| `X 를 하면 안 되는 이유는?` | 하면 깨지는 것 | 대신 하는 법(선택), `- 전제: …`(확인했으면) |
| `X 에서 쓸 수 있는 Y 는?` | 요약 한 문장 | 항목마다 한 줄 |

좋은 예:

```
Q. fast-question 검색창에서 쓸 수 있는 질의 문법은?
A. 공백으로 나눈 단어는 모두 들어 있어야 찾고(AND), kb/query.py 가 해석한다.
   - a | b: 둘 중 하나(OR)
   - -a: 제외
   - "a b": 공백을 포함한 구절
   - q:a · a:a: 질문만 · 답변만
   - path:파일이름: 그 파일을 근거로 단 항목
```

```
Q. fast-question 에 등록분을 사람이 승인하는 화면이 없는 이유는?
A. 등록분은 kb_add 의 형식 검사와 근거 판정으로 거르고, 사람이 건마다 승인하는 단계를 두지 않는다.
   - 틀린 항목은 웹 화면의 편집이나 kb_update 로 그 자리에서 고친다
   - 전제: 한 사람이 쓰고 Claude 가 등록한다. 여러 사람이 서로의 등록분을 승인해야 하면 다시 판단한다
```

나쁜 예와 고칠 점:

- `fast-question 의 미검토 표시는 언제 붙나? / 붙지 않는다. 사람 검토 기능은 2026-10-08 사용자 결정으로 지웠고 …`
  없는 표시를 묻고 답은 결정 경위(날짜, 정한 사람)다. 질문을 위 좋은 예처럼 `… 화면이 없는 이유는?` 로 바꾸고, 답에는 지금 유효한 이유와 전제를 쓴다. 날짜와 정한 사람은 note 근거에 둔다.
- `cnd-lea-be 서비스들의 jasypt 설정은 어느 yml 에 있나? / jasypt 블록(bean, algorithm, 키 환경변수)은 … 에 있고, datasource 접속값은 ENC(...) 형태다. lea-auth 는 …`
  위치를 물었는데 설정 내용과 다른 서비스 이야기가 섞였다. 첫 줄은 위치만 쓰고, 나머지는 질문을 나눠 따로 등록한다.
- `fast-question 요청 제한 값을 설정으로 바꿀 수 있나? / 없다. 코드 상수다.`
  다음에 무엇을 할지 알 수 없다. 값이 어느 파일의 어떤 상수에 있는지, 바꾸면 무엇을 다시 시작해야 하는지를 항목으로 붙인다.

## 분류

- 대분류는 작업 주제(프로젝트·사업 이름, `일반 지식`), 중분류는 대상(모듈, 시스템, 기술)이다.
- 대분류 이름은 사용자가 그 작업을 부르는 이름으로 짓는다. 이미 있는 대분류가 있으면 그 이름을 따른다.
  참고: 즉석 질문 훅은 질문한 폴더 경로의 한 단계 이름이 대분류 이름과 같거나, qa-harvest 로 구축한 경로 또는 Q&A 의 파일 근거가 놓인 폴더와 겹치면 그 폴더를 프로젝트로 보고 등록 안내를 붙인다.
- 항목이 10건을 넘는 기술 분야(예: Kubernetes)는 그 기술 이름을 대분류로 쓰고, 중분류는 그 기술의 하위 주제(스토리지, 네트워크)로 한다. 몇 건뿐인 기술은 `일반 지식 > <기술 이름>` 에 둔다.
- 한 대상의 항목을 두 대분류에 나누지 않는다. 기술 대분류의 하위 주제로 다루는 내용(예: Kubernetes 볼륨으로 쓰는 NFS)은 그 기술 대분류에, 기술 자체의 일반 사실(예: NFS 프로토콜)은 `일반 지식` 에 둔다.
- `kb_categories` 의 분류 설명(description)에 그 분류의 범위가 적혀 있으면 따른다.
- `kb_categories` 에 맞는 분류가 없으면 묻지 않고 `kb_add_category` 로 만든다. 대분류가 있으면 그 아래 중분류만 만든다.

## 근거

| 사실을 확인한 곳 | 근거 |
|---|---|
| 이 세션에서 읽은 로컬 파일(코드, 설정, md) | `{"kind": "auto", "path": "<절대경로>", "anchor": "<심볼이나 찾을 문자열>"}` |
| 문서 파일(xlsx, hwp, pdf, docx) | `auto` + `path`. 시트 이름이나 절 제목을 `anchor` 로 쓴다 |
| git 이력(커밋) | 그 사실이 지금 남아 있는 파일을 `auto` 로 달고, 답변에 커밋 sha 앞 7자리를 쓴다 |
| 웹 문서 | `{"kind": "url", "url": "<주소>"}` |
| GitHub 저장소의 파일 | `{"kind": "github", "url": "https://github.com/<owner>/<repo>/blob/<브랜치 또는 커밋>/<경로>", "anchor": "<찾을 문자열>"}`. 서버가 blob sha 로 바뀜을 판정한다(원격 서버에서도 된다). 그 밖의 웹 주소는 `url` 이다 |
| 사람에게 확인 | `{"kind": "note", "text": "누가 어떻게 확인했는지"}` |
| 쓰지 않기로 한 것, 없앤 것 | 정한 사람과 날짜를 `note` 에 쓴다(`"사용자가 2026-10-08 대화에서 정함"`). 그 결정을 적은 문서를 이 세션에서 읽었으면 그 파일을 함께 단다 |
| 해 보고 안 된 방법 | `{"kind": "note", "text": "이 세션에서 <명령> 을 실행해 <결과> 를 확인"}`. 원인이 있는 파일을 읽었으면 그 파일을 함께 단다 |
| 일반 지식 | 근거 없음. 학습 문서·공식 문서처럼 출처 주소가 있으면 `url` 근거를 단다 |

- 이 세션에서 읽지 않은 파일은 근거로 달지 않는다.
- git 저장소 안의 파일은 `auto` 가 git 근거로 기록된다.
- 파일 하나를 가리키는 근거의 `anchor` 는 그 파일에 그대로 있는 문자열이어야 한다. 없으면 등록이 거부된다. 폴더·여러 경로 근거와 xlsx·docx·hwp·pdf 같은 압축·이진 문서는 확인하지 않는다.

## 용어

- 형태소 분석이 잘못 자르는 고유명사(시스템 이름, 사업 이름)는 등록 전에 `kb_dict_edit` action=user_word_add 로 넣는다. 색인을 다시 만든다. 원격 서버에 연결했으면 이 동작은 거부된다(서버 공용 사전이라 운영자가 넣는다). 넣지 말고 넘어간다.
- 같은 뜻의 다른 표기(규칙/룰, NAS/스토리지)는 `kb_dict_edit` action=synonym_add 로 묶는다.
