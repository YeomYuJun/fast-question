# Q&A 등록 규칙

이 파일이 fast-question 등록 규칙의 원본이다. qa Skill, qa-harvest Skill, MCP 서버 안내문은 이 파일을 따른다.
Claude 가 MCP 로 쓸 때 `kb_add`·`kb_add_many`·`kb_update`·`kb_evidence` 는 답변 양식, 금지 표현, 민감 정보를 검사해 위반이면 거부한다. 거부 메시지를 보고 고쳐서 다시 부른다.

DB 는 사실만 담는다. 등록할지 망설여지면 등록하지 않는다. 사람은 등록분을 검토하지 않으므로 한 건이 틀리거나 쓸모없으면 그대로 남는다.

## 넣는 것

- 동작: 무엇이 언제 무엇을 하는지, 실패하면 어떻게 되는지
- 이유: 코드·설정이 지금 그렇게 되어 있는 이유(원문에서 확인한 것만)
- 절차: 무엇을 하려면 어떤 명령을 어떤 순서로 쓰는지
- 위치: 설정·문서·값이 어느 파일·시트에 있는지
- 오류의 원인과 처리
- 설정 키·값·코드의 뜻
- 작업에 실제로 쓰여 답을 확인한 일반 지식

## 넣지 않는 것

- 결정 경위(누가 언제 무엇을 정했는지), 개발 이력, 바뀌기 전의 동작. 지금 동작과 그 이유만 쓴다
- 내부 구현 세부(테이블 열, 내부 함수 이름)로만 답이 되는, 사용자가 다시 물을 일이 없는 것
- 진행 상태, 할 일, 일정
- 이름만 봐도 아는 것(예: `UserService 는 사용자 서비스인가`)
- 코드나 문서를 그대로 옮긴 것
- 확인하지 않은 추정. 확인하지 못했으면 등록하지 않는다
- 이 대화에만 해당하는 질문(예: `방금 그 명령은 왜 실패했나`)
- 지금 작업 중인 프로젝트와 무관한 평시 질문(언어 문법, 도구 사용법, 개념). 사용자가 `/qa` 로 요청할 때만 넣는다
- 비밀번호, 토큰, API 키, 개인 키
- 주민등록번호, 전화번호, 이메일 주소 같은 개인정보
- IP 주소 같은 내부 망 값. 값 대신 그 값이 적힌 위치(파일·시트)와 절차를 쓴다. 루프백(`127.0.0.1`)은 넣어도 된다

## 질문

- 한 줄, 150자 이하. 글자 수는 공백을 포함한 문자 수다(한글·영문·기호 모두 1자).
- 한 질문에 한 사실만 묻는다. 대상이 `와·및·그리고·,` 로 둘 이상 묶이면 질문을 나눈다. 비교·차이를 묻는 질문(`A 와 B 의 차이는?`)은 한 사실이라 나누지 않는다.
- 질문만 읽어도 무엇에 대한 것인지 알 수 있게 쓴다. 대상 이름(파일, 클래스, 설정 키, 명령, 개념)을 넣는다.
  대상이 일반 명사(검색, 분류, 웹 서버, 저장소, 배포)면 시스템이나 프로젝트 이름을 붙인다.
  - 나쁨: `검색 문법은`
  - 좋음: `fast-question 검색창에서 쓸 수 있는 질의 문법은?`
- 묻는 문장으로 쓴다. 물음표는 붙여도 되고 붙이지 않아도 된다.

## 답변

- 400자 이하, 6줄 이하. 글자 수는 공백과 줄바꿈을 포함한 문자 수다.
- 답에는 질문에 필요한 만큼 동작(무엇이 무엇을 해서), 결과(그래서 어떻게 되는지), 확인하거나 처리하는 법을 넣는다. `없다`, `코드 상수다` 처럼 다음에 무엇을 할지 알 수 없는 한 문장으로 끝내지 않는다.
- 첫 줄만으로 끝나는 짧은 사실은 같은 대상의 관련 사실과 묶어 한 항목으로 만든다. 질문의 대상은 하나로 두고, 둘째 줄부터 그 대상의 다른 측면(바꾸는 곳, 기본값, 예외)을 쓴다.
- 첫 줄은 질문에 바로 답한다. 1~2문장, 120자 이하. 질문이 묻지 않은 대상(다른 모듈·서비스)은 쓰지 않는다.
- 둘째 줄부터는 필요할 때만 쓴다. `- ` 로 시작하고 한 줄에 한 사실을 개조체로 쓴다(마침표 없이, 120자 이하).
  한 줄에 사실을 쉼표로 이어 붙이지 않는다. 120자를 넘을 내용이면 항목으로 나눈다.
- 무엇이 무엇을 해서 어떻게 되는지 쓴다. 비유를 쓰지 않고 얼버무리지 않는다.
- 경로, 식별자, 명령은 원문 그대로 쓴다.
- 측정값, 버전에 따라 바뀌는 내용에는 기준을 붙인다(예: `2026-10-08 실측 2.5초`, `kiwipiepy 0.24.0 기준`).

질문 문형이 답 모양을 정한다.

| 질문 | 첫 줄 | 둘째 줄부터 |
|---|---|---|
| `X 하려면?` | 명령이나 첫 동작 | 이어지는 동작을 순서대로 |
| `X 의 뜻은?`, `X 는 무엇인가?` | `X 는 …다.` | 없음 |
| `X 가 Y 하는 이유는?` | `…때문이다.` | 그 결과(선택) |
| `X 는 어디에 있나?` | 경로·위치 | 그 위치에 무엇이 있는지(선택) |
| `X 가 실패하면?`, `X 는 언제 Y 하나?` | 조건과 결과 | 예외 조건(선택) |
| `X 에서 쓸 수 있는 Y 는?` | 요약 한 문장 | 항목마다 한 줄 |

좋은 예:

```
Q. fast-question 검색창에서 쓸 수 있는 질의 문법은?
A. 공백으로 나눈 단어는 모두 들어 있어야 찾고(AND), kb/query.py 가 해석한다.
   - a | b: 둘 중 하나(OR)
   - -a: 제외
   - "a b": 공백을 포함한 구절
   - q:a · a:a: 질문만 · 답변만
   - path:파일이름: 그 파일을 근거로 단 항목
```

나쁜 예와 고칠 점:

- `fast-question 의 미검토 표시는 언제 붙나? / 붙지 않는다. 사람 검토 기능은 2026-10-08 사용자 결정으로 지웠고 …`
  없는 기능의 결정 경위다. 사용자가 다시 물을 일이 없다. 등록하지 않는다.
- `cnd-lea-be 서비스들의 jasypt 설정은 어느 yml 에 있나? / jasypt 블록(bean, algorithm, 키 환경변수)은 … 에 있고, datasource 접속값은 ENC(...) 형태다. lea-auth 는 …`
  위치를 물었는데 설정 내용과 다른 서비스 이야기가 섞였다. 첫 줄은 위치만 쓰고, 나머지는 질문을 나눠 따로 등록한다.
- `fast-question 요청 제한 값을 설정으로 바꿀 수 있나? / 없다. 코드 상수다.`
  다음에 무엇을 할지 알 수 없다. 값이 어느 파일의 어떤 상수에 있는지, 바꾸면 무엇을 다시 시작해야 하는지를 항목으로 붙인다.

## 분류

- 대분류는 작업 주제(프로젝트·사업 이름, `일반 지식`), 중분류는 대상(모듈, 시스템, 기술)이다.
- 대분류 이름은 사용자가 그 작업을 부르는 이름으로 짓는다. 이미 있는 대분류가 있으면 그 이름을 따른다.
  참고: 즉석 질문 훅은 질문한 폴더 경로의 한 단계 이름이 대분류 이름과 같거나, qa-harvest 로 구축한 경로 안이면 그 폴더를 프로젝트로 보고 등록 안내를 붙인다.
- 항목이 10건을 넘는 기술 분야(예: Kubernetes)는 그 기술 이름을 대분류로 쓰고, 중분류는 그 기술의 하위 주제(스토리지, 네트워크)로 한다. 몇 건뿐인 기술은 `일반 지식 > <기술 이름>` 에 둔다.
- 한 대상의 항목을 두 대분류에 나누지 않는다. 기술 대분류의 하위 주제로 다루는 내용(예: Kubernetes 볼륨으로 쓰는 NFS)은 그 기술 대분류에, 기술 자체의 일반 사실(예: NFS 프로토콜)은 `일반 지식` 에 둔다.
- `kb_categories` 의 분류 설명(description)에 그 분류의 범위가 적혀 있으면 따른다.
- `kb_categories` 에 맞는 분류가 없으면 묻지 않고 `kb_add_category` 로 만든다. 대분류가 있으면 그 아래 중분류만 만든다.

## 근거

| 사실을 확인한 곳 | 근거 |
|---|---|
| 이 세션에서 읽은 로컬 파일(코드, 설정, md) | `{"kind": "auto", "path": "<절대경로>", "anchor": "<심볼이나 찾을 문자열>"}` |
| 문서 파일(xlsx, hwp, pdf, docx) | `auto` + `path`. 시트 이름이나 절 제목을 `anchor` 로 쓴다 |
| git 이력(커밋) | 그 사실이 지금 남아 있는 파일을 `auto` 로 달고, 답변에 커밋 sha 앞 7자리를 쓴다 |
| 웹 문서 | `{"kind": "url", "url": "<주소>"}` |
| 사람에게 확인 | `{"kind": "note", "text": "누가 어떻게 확인했는지"}` |
| 일반 지식 | 근거 없음. 학습 문서·공식 문서처럼 출처 주소가 있으면 `url` 근거를 단다 |

- 이 세션에서 읽지 않은 파일은 근거로 달지 않는다.
- git 저장소 안의 파일은 `auto` 가 git 근거로 기록된다.

## 용어

- 형태소 분석이 잘못 자르는 고유명사(시스템 이름, 사업 이름)는 등록 전에 `kb_dict` action=user_word_add 로 넣는다. 색인을 다시 만든다. 원격 서버에 연결했으면 이 동작은 거부된다(서버 공용 사전이라 운영자가 넣는다). 넣지 말고 넘어간다.
- 같은 뜻의 다른 표기(규칙/룰, NAS/스토리지)는 `kb_dict` action=synonym_add 로 묶는다.
